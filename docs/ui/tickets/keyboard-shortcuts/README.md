## 控制粒度与预重构

- 不拆成协议、数据、宿主、UI、测试五类水平工单，每单沿实际用户流程覆盖需要改动的层。
- 查询与搜索共用面板和操作目录，合并为 01；绑定保存、冲突和实际事件分发密切相关，合并为 02，避免交付只修改显示、不改变实际按键的中间结果。
- 03 包含真实的插件停用、配置保留和恢复冲突行为，不是独立的“只做测试”工单。最终短组合验收随它交付，不额外拆单。
- 当前没有证据表明必须进行独立的广域机械重构。必要预重构放在所属工单最前面，先做行为保持的职责整理并验证，再增加新行为；不为拆单新增 crate 或薄转发接口。
- 01 先把既有操作和作用域接入一致的描述入口，保留原有执行行为；02 再接入有效绑定和统一分发，迁移完成后撤销重复旧绑定路径。每单保持可编译、可验证，不用永久双分发兼容层掩盖未迁移路径。
- 01 的查询阶段与 02 的配置阶段都是可演示的增量，不代表完整功能可最终验收。整项功能完成须以 03 结束后的全部验收覆盖为准。

## 减少重复测试的执行规则

1. 每单开发中先运行受影响的针对性测试，完整阶段检查集中在该单交付前；不为每个字段或控件重复全量检查。
2. 仓库要求的每阶段检查保留：`cargo fmt --check`、`cargo test --workspace --exclude editor-app`、`cargo check --workspace`。三单对应三个交付阶段，不把“减少重复”解释成只在最终阶段运行规定检查。
3. 修改 editor-app 时执行相关 GPUI 测试和必要的原生交互验收。各场景明确归属，后续未修改相应行为时引用已有验证记录，不把整份手工矩阵每单重演。
4. 共用临时用户配置、工作区、可控时钟和插件包夹具。测试数据按场景隔离；输入、SDK、依赖和工具链未变时复用构建产物，不反复清理和重打包。
5. 修改公开契约、SDK 或实际包时，仍执行要求的消费者、SDK 分发、打包和相关 ignored 验证；夹具准备在同一交付阶段内复用，不以旧产物证明新契约。
6. 每单记录测试对应的提交或工作树、包身份、命令与结果。后续改变相应路径、有失败或未解决风险时重跑受影响场景，不能把历史结果当作当前版本刚运行通过。
7. 03 最后只增加一次短组合验收：从不同面板查询 → 修改一个基础编辑绑定和一个插件绑定 → 测试两步执行及冲突 → 插件禁用/恢复 → 重启后复验绑定和焦点。复用前两单详测证据，不完整重复所有手工场景。
8. 无新增改动、失败或未解决问题时，不重复已经通过的相同检查。每单必要的格式、构建和行为保持验证不省略。
