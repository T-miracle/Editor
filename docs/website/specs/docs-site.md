# 编辑器文档站点规格

Status: ready-for-agent — 规格与工单拆分已确认；测试接缝已由用户确认（两个接缝，见 Testing Decisions）。
已发布：[GitHub #38](https://github.com/T-miracle/Editor/issues/38)。工单 #39–#47 见[工单索引](../tickets/README.md)，14 条原生阻塞边已建立并读回核对。
依据：[静态文档站点方案](static-docs-site.md)（决策记录、目录树、迁移映射、防漂移机制、风险）。

## Problem Statement

编辑器目前没有给使用者看的文档。想学会打开文件、编辑、跳转定义或安装插件的人，只能读仓库的 `docs/`——那是 AI 与维护者的工作资料（需求基线、方案、工单、验收记录），既不是产品说明，也不适合直接发布。写插件的人情况类似：插件 SDK 的协议契约、能力协商方式、独立构建入口散落在源码旁与插件包说明里，没有一处能从头读到尾的公开文档。

由此产生四个具体问题：

1. 使用者无处可查"这个编辑器怎么用"，包括快捷键、面板布局、设置与主题。
2. 使用者不知道插件怎么安装、权限如何确认、受限工作区有什么限制。
3. 插件作者必须克隆仓库才能读到能力协议，且读到的可能是与当前编辑器版本无关的历史描述。
4. 仓库里的中文与英文文档混在一起，读者无法判断哪一份是权威、哪一份是最新。

## Solution

为读者建立独立的文档站点，与 `docs/` 工作资料彻底分开，并部署到 GitHub Pages 供直接访问。

站点分两条线：**编辑器使用**（面向使用者）与**插件系统对接**（面向插件作者）。站点从一开始就是中英双语，英文为权威正本、中文为译文，两侧页面一一对应。

插件能力协议的正文从源码旁迁到站点成为唯一手写源，同时保留"随编辑器分发的 SDK 目录内仍带有这些文档"这一既有行为——插件作者用 `--export-plugin-sdk` 或 `--plugin-cargo` 时读到的文档与站点上发布的完全一致。插件包自己的 README 不进站点，它仍然是插件包内容，由插件管理界面读取显示。

站点不发布任何内部资料：工单、验收记录、协作约定、方案留在 `docs/`。仓库根 README 保留开发者视角的运行与构建说明，使用者文档以站点为准。

## User Stories

### 使用者

1. As a 编辑器使用者, I want 在独立站点上读到完整的编辑器使用说明, so that 不必读仓库里的工程文档就能上手。
2. As a 编辑器使用者, I want 看到界面区域与停靠面板的说明, so that 知道文件树、编辑区与插件面板如何组合。
3. As a 编辑器使用者, I want 查到快捷键与鼠标操作, so that 掌握保存、跳转定义、错误跳转等操作。
4. As a 编辑器使用者, I want 了解文件树、忽略规则与搜索范围, so that 理解为什么某些文件不显示。
5. As a 编辑器使用者, I want 了解设置与主题的作用范围, so that 知道项目设置不会覆盖我的个人偏好。
6. As a 编辑器使用者, I want 了解受限工作区会限制什么, so that 明白为什么某些插件或语言工具没有启动。
7. As a 中文读者, I want 有等价的中文页面, so that 不必读英文。
8. As a 英文读者, I want 权威英文页面不被中文翻译拖后, so that 读到的是最新契约。
9. As a 读者, I want 用语言切换在两个版本间跳转并停在对应页面, so that 切换后不迷路。

### 插件作者

10. As a 插件作者, I want 从头读到尾的 SDK 文档, so that 不必克隆仓库或翻源码。
11. As a 插件作者, I want 了解协议版本与能力协商, so that 知道该声明什么、编辑器会检查什么。
12. As a 插件作者, I want 在本地就读到同一份文档, so that 离线开发时也有依据。
13. As a 插件作者, I want 知道哪些接口是权威英文版, so that 出现分歧时以正确的一份为准。
14. As a 插件作者, I want 站内搜索命中协议关键词, so that 快速定位某个能力。
15. As a 插件作者, I want 从文档跳到插件包与示例, so that 找到可运行的参考。

### 使用者：插件管理

16. As a 编辑器使用者, I want 读到插件安装与权限确认流程, so that 首次安装时不意外授予权限。
17. As a 编辑器使用者, I want 了解启停、更新与卸载后的状态, so that 知道何时会保留或撤销资源。
18. As a 编辑器使用者, I want 了解各插件自己的用法在哪里查, so that 知道去插件管理界面读包内说明。

### 维护者

19. As a 维护者, I want 双语页面必须同时更新并被测试拦住, so that 中文翻译不会悄悄过期。
20. As a 维护者, I want 断链在构建阶段就被发现, so that 线上不出现 404。
21. As a 维护者, I want 站点目录移动时编译立刻失败, so that 不会发布缺少 SDK 文档的编辑器。
22. As a 维护者, I want 站点只发布最新文档并标注适用版本, so that 不必维护历史版本树。
23. As a 维护者, I want 内部工单与验收记录不出现在公开站, so that 工作资料不外泄。
24. As a 维护者, I want 推送后自动构建部署, so that 不必手工执行发布。

## Implementation Decisions

### 工作面与目录

- `docs/` 保持为 AI 与维护者工作面，不发布；读者文档全部手写在 `website/`。
- 站点在 `en/` 与 `zh-CN/` 下平行组织，页面路径一一对应，每页提供指向对侧同一页面的切换入口。
- 站点不引入版本目录（不建 `/versions/`）；页内保留 `protocol = 7`、`api.base ^1` 等版本表述，首页标注当前适配的编辑器版本。

### 内容来源

- 插件能力协议正文从 `crates/plugin-protocol/` 迁入站点，成为唯一手写源；该 crate 只保留指向站点的指针。
- 迁移映射：原 `README.md` 拆为 SDK 概览与独立构建两页，`UI.md`、`SERVICES.md`、`PROCESSES.md`、`LANGUAGES.md`、`LSP.md`、`DEPENDENCIES.md`、`MIGRATION.md`、`FAULTS.md` 各成一页。
- 语言现状：`DEPENDENCIES.md`、`MIGRATION.md`、`LANGUAGES.md`、`FAULTS.md` 正文已是英文；`README.md`、`UI.md`、`PROCESSES.md`、`SERVICES.md`、`LSP.md` 正文为中文，需产出英文权威版并把中文原文转为译文。
- 翻译必须保留字节数、条目上限、错误码、版本号与权限名称等精确表述，不得改写语义；不得为行文流畅而放宽或收紧任何限制描述。
- 站点不收录插件包 README；`plugins/<包>/README.md` 仍是插件包内容，由插件管理界面读取显示。
- 站点不收录清单与资源格式章节（`manifest.json`、`plugin.toml`、`icons.json` 的字段参考）；正本在 `crates/plugin-schema/` 的 Rust 类型中，需要独立盘点后再定章节。

### 与 SDK 分发的关系

- SDK 导出的文件集合保持不变：仍导出协议文档、WIT、Rust 源码与 `Cargo.toml`；改变的只是这些文件的来源路径。
- 内容摘要缓存的既有语义不变：接口内容变化即换摘要目录，不同编辑器版本各自持有缓存。
- 导出取英文权威版；中文页面只服务站点读者，不进入 SDK 载荷。
- 站点 SDK 文档目录的移动或改名必须导致 Rust 编译失败，这是有意建立的耦合，需在站点协作约定中明确警告。

### 站点工程

- 采用 Astro 自建管线，参照同为主仓库内 `website/` 布局的既有实践；不使用现成文档主题。
- 不做数学公式渲染、不做交互式组件演示。
- 只做两个自定义 Markdown 插件：提示框（大量使用）与源码片段引入（用于从实现引用快捷键等易漂移内容，避免手抄）。
- 站内搜索使用构建期生成的静态索引，中英两棵树都参与索引。

### 部署

- 目标为 GitHub Pages 项目站，资源根路径带仓库名前缀；配置文件中的站点地址与根路径需相邻注释说明仓库改名时同步修改。
- 仓库此前没有 CI，部署流水线从零新建，构建前先运行站点测试，失败不部署。
- 首次上线需用户在仓库设置中把 Pages 来源切到 GitHub Actions。

### 已确认的交互与行为约束

- 语言切换必须在对应页面上互跳，而不是回到首页。
- 侧栏导航按"使用指南 / 插件系统对接"两条线组织，与页面目录一致。
- 站点不出现任何指向 `docs/` 内工单、验收记录或协作约定的链接。

## Testing Decisions

以下测试边界已由用户确认：**两个接缝，都取现有或最高的层级，不新增临时命令。**

### 良好测试的说明

只验证外部可观察结果：站点能构建、页面存在且可访问、链接与锚点可解析、双语页面集合一致、导出的 SDK 目录内容正确。不断言内部辅助函数、remark 插件的实现细节或页面 DOM 结构。

### 接缝一：现有 `scripts/verify-plugin-sdk.ps1` 与 `--export-plugin-sdk`（复用，不新增）

- 覆盖 SDK 侧风险：文档来源改指站点目录后，导出文件集合、内容哈希与损坏修复仍正常；插件作者的独立构建与安装路径不受影响。
- 该脚本已在契约层面校验导出目录的文件存在性与哈希一致性，迁移后应继续通过；若失败，先判断是内容缺失还是路径错误，不修改脚本断言来迁就实现。
- 需要真实 WASM 的用例按其 ignore 原因先构建夹具再显式运行，不把跳过的测试报告为通过。

### 接缝二：站点构建与 `website/tests/`（新增，唯一新接缝）

- `tests/links`：站内链接、锚点与跨语言切换链接可解析；外部链接可达性按需检查，避免把网络波动当成缺陷。
- `tests/doc-sources`：两个语言树的页面路径集合一致（缺页与多页都失败）；每页包含指向对侧页面的切换入口；必填的页面元数据存在。
- 构建本身即是验证的一部分：站点构建产物存在、双语路由可访问。
- 不为两个自定义 Markdown 插件单独写单元测试；它们的行为由真实页面构建与链接测试覆盖。

### 可借鉴的先例

- SDK 分发与独立构建：`crates/plugin-runtime` 的 SDK 分发集成测试与 `verify-plugin-sdk.ps1` 的组合。
- 文档类改动的检查方式：仓库约定对纯文档变更要求核对链接、路径与命令一致性，本次站点测试是这一要求的机制化。

### 实施阶段必须执行的检查

- 站点侧：站点构建、站点测试、本地预览核对中英两版与搜索。
- Rust 侧（迁入 SDK 文档后）：格式检查、非 UI workspace 测试、workspace 编译检查。
- SDK 链路：先构建宿主可执行文件，再运行 SDK 验证脚本。
- 证据记录实际命令、结果、跳过项与平台限制；不以构建通过替代真实页面核对。

## Out of Scope

- 插件清单与资源格式（`manifest.json`、`plugin.toml`、`icons.json`、`plugin-schema` 字段参考）章节，以及 `docs/plugins/主题插件格式.md` 的归属。
- 各插件自己的用法（终端、SVG、Rust、HTML、JavaScript、TOML），它们留在插件包 README 与插件管理界面。
- 在线市场、评论、评分等需要在线服务的功能。
- 按编辑器版本发布历史文档（`/versions/`）。
- 站点登录、评论系统、分析埋点、自定义域名与证书。
- 数学公式渲染与交互式组件演示。
- 把 `docs/` 内部资料整理为公开文档，或改变 `docs/` 的现有分类结构。

## Further Notes

### 当前阻塞实施的前置条件

- **Node 工具链未安装**：本地无法构建与预览站点，也无法运行站点测试。工单 E01 的第一步就是该前置检查；未满足前不开始编码，也不擅自安装（仓库约定要求先核对目标工具链、不擅自安装缺失工具）。
- **无 GitHub 写凭据**：本规格与工单暂存本地，发布方式待用户决定。
- **GitHub Pages 未启用**：`has_pages: false`，需用户切换 Pages 来源；这是工单 E07 的外部前置，不由代理完成。

### 风险提示

- 仓库首次引入 Node 与 npm 生态，`package.json` 与自定义 Markdown 插件构成新的维护面。
- 迁移后的文档是"跨目录引用"：站点目录改名会直接导致 Rust 编译失败，属于有意耦合。
- 项目站资源根路径带仓库名前缀，缺失会导致线上 404；部署工单必须核对真实子路径下的链接。
- 双语维护成本真实存在：协议变更需同一次提交改两份，测试只能保证页面对应，不能保证语义等价，审查时需逐条对照精确表述。

### 与其他批次的关系

本批独立于已完成的插件平台 20 张工单，也独立于 Markdown 插件批次（父方案 #26）。三者共用同一跟踪器约定与提交、关闭流程，但本批不修改既有父议题，也不继承其完成状态。

### 验收覆盖

规格验收项与本规格的用户故事、方案"验证计划"一一对应；每张工单声明其覆盖的用户故事编号，由 E09 执行最终集成复核。覆盖编号不是测试已通过的声明。
