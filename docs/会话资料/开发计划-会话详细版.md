# Me Editor 开发计划

本文将已确认的产品需求转化为项目实施顺序。详细需求见工作区根目录的 `需求整理.md`；本计划以当前仓库已具备的编辑闭环为起点，不重做已完成能力。

## 当前基线

当前项目已经具备：

- Windows 上可运行的 GPUI Kit 三段式编辑器界面；
- `.gitignore` 感知的文件树；
- UTF-8 文件打开、编辑、保存、基础高亮、折叠、行号和软换行；
- 会话内编辑历史与保存前本地快照；
- `plugin-schema` 和统一命令注册表骨架；
- `editor-app`、`editor-core`、`platform-windows`、`plugin-schema` 四个 crate。

后续开发不得破坏这一基础编辑闭环。每个阶段结束时均应通过既有格式化、测试和编译检查。

## 实施原则

- `EditorState` 是唯一的内存文本、IME、选择、布局和会话 Undo/Redo 真相来源。
- 语法高亮不再依赖宿主内建 grammar；所有 grammar 必须来自已启用语言插件携带的 Tree-sitter WASM 文件。
- 外部 Node、Rust、Git、LSP 和格式化器均不捆绑、不自动安装，只探测、校验和调用。
- 任何异步语言结果必须携带文档 revision；过期结果不得写入当前编辑状态。
- 项目设置不能覆盖用户语言、主题和工作区信任；破坏性 Git 与批量替换必须预览并确认。

## 阶段 0：基线验证与依赖锁定

目标：确认现有编辑器在目标 Windows 环境可稳定运行，并记录可复现依赖版本。

工作：

1. 运行 `cargo fmt --check`、`cargo test --workspace --exclude editor-app` 与 `cargo check --workspace`。
2. 记录 Rust、GPUI Kit、Tree-sitter、Windows 工具链版本。
3. 为打开文件、编辑、保存、历史快照和 `.gitignore` 文件树补齐回归测试。
4. 固定可运行的最小示例工作区，供后续阶段验收。

完成标准：基础编辑闭环在测试与人工运行中稳定；新增后续能力不会依赖未锁定版本。

## 阶段 1：动态 WASM grammar 技术验证

目标：证明“高亮完全来自插件”可在不 fork GPUI Kit 编辑内核的前提下成立。

工作：

1. 在 `plugin-schema` 定义版本化 `plugin.toml`：插件 ID、宿主版本、Tree-sitter ABI、grammar 文件、查询文件、文件匹配和权限声明。
2. 在 `editor-core::language_host::syntax` 建立 WASM grammar 加载器，使用 Tree-sitter 的 WASM 支持校验 ABI 与内容 hash。
3. 实现 `DocumentSession → revision 快照 → 后台增量解析 → HighlightSpans` 流程。
4. 通过 GPUI Kit 的公开高亮接缝渲染插件产生的范围，替换当前按扩展名使用的宿主高亮路径。
5. 制作本地 Rust 与 TypeScript 插件作为验证样本。

完成标准：关闭任一插件后对应语言没有高亮；启用本地插件后高亮恢复。连续输入期间，过期解析结果不会覆盖较新 revision。

## 阶段 2：插件安装、依赖与项目启用

目标：实现声明式、按项目启用的语言插件体系。

工作：

1. 在 `editor-core::plugins` 实现本地目录安装、公开 GitHub 链接安装、commit/hash 锁定和显式更新。
2. 建立全局安装记录与本机工作区启用记录；项目仓库仅保存推荐插件和版本范围。
3. 实现依赖解析、版本约束、循环检测和自动启用所需依赖。
4. 安装时展示权限；项目启用时不重复提示。
5. 完成 HTML、CSS、JavaScript、TypeScript、Vue、React、Rust 七个独立插件的 grammar 与查询文件。

完成标准：不同项目可启用不同插件集；Vue/React 等依赖项能自动解析；GitHub 插件重新打开项目时不发生静默更新。

## 阶段 3：工作区信任、设置与外部工具链

目标：安全地把项目配置与用户安装的工具连接到插件。

工作：

1. 实现受限工作区与受信任工作区状态；受限状态不得启动插件或外部工具。
2. 实现用户、共享项目、本机工作区三类设置作用域及合法性校验。
3. 实现 Node、Rust、Git 的路径解析：项目本地 → 项目覆盖 → 用户全局 → PATH/注册表/常见目录。
4. 建立工具版本校验、缓存与失效机制；不得自动安装工具。
5. 工具缺失时实现部分降级与可操作诊断。

完成标准：不受信任项目不会启动 LSP；同一插件在不同项目可使用不同工具路径；缺少工具时仍可编辑和高亮。

## 阶段 4：LSP 与格式化

目标：接入外部语言能力，并确保其不会破坏编辑一致性。

工作：

1. 建立仅支持标准输入输出 JSON-RPC 的 LSP 传输、请求关联、取消、超时和退出恢复。
2. 支持诊断、补全、悬浮信息、语义 token 与格式化返回的文本编辑。
3. 先接入 `rust-analyzer`、TypeScript 语言工具和 Volar；路径全部来自 `toolchains`。
4. 支持手动格式化；项目可按语言配置保存时格式化。
5. 为 LSP 乱序响应、工具崩溃、版本不符和格式化冲突建立测试。

完成标准：Rust、TypeScript 与 Vue 项目能显示诊断；格式化仅应用到匹配 revision 的文本；语言工具崩溃不影响编辑器继续使用。

## 阶段 5：搜索、替换与本地历史

目标：完成项目级文本操作与跨会话恢复。

工作：

1. 实现遵循 `.gitignore` 与 `files.exclude` 的流式搜索，支持文本、大小写、全词和正则。
2. 搜索已打开文件时读取内存快照，未打开文件读取磁盘。
3. 实现版本固定的替换计划、预览、确认、原子写入和冲突跳过报告。
4. 将本地历史升级为 SQLite 元数据、压缩增量和周期性完整检查点。
5. 实现版本浏览、恢复计划、30 天或 1 GB 清理以及重启恢复。

完成标准：批量替换不会覆盖执行期间被修改的文件；未保存内容可在重启后恢复；本地历史不写入项目目录。

## 阶段 6：完整 Git 交互

目标：在不管理凭据的前提下提供可用的本地与远程 Git 操作。

工作：

1. 建立每仓库串行写入队列、结构化 porcelain/diff/log 解析与刷新机制。
2. 实现状态、diff、历史、暂存、取消暂存、提交、创建/切换分支。
3. 实现 clone、fetch、pull、push，并原样复用外部 Git 的 Credential Manager 与 SSH Agent。
4. 对丢弃修改、reset、覆盖式 pull 和强制切换实现影响预览与明确确认。

完成标准：常规 Git 工作流不需要在编辑器保存密码；破坏性动作无法跳过确认；Git 操作后的文件状态会刷新到工作区和已打开文档。

## 阶段 7：产品收尾与 Windows 交付

目标：把功能闭环打磨为可发布的 Windows 初版。

工作：

1. 完成英文/简体中文文案、首次语言选择、深浅主题与可访问性检查。
2. 完成固定三栏布局、大小调整与会话恢复体验。
3. 补齐命令面板、快捷键设置与冲突提示。
4. 进行大文件、中文 IME、文件变更、插件损坏、工具缺失和 Git 网络失败的人工验收。
5. 建立 Windows 安装包、升级策略、第三方许可清单和发布检查表。

完成标准：在干净 Windows 环境中，用户可以安装应用、配置外部工具、打开/信任项目、启用语言插件、编辑/格式化/搜索、进行 Git 操作并恢复历史。

## 模块依赖顺序

```text
plugin-schema
      ↓
documents + 动态 syntax
      ↓
plugins + workspace trust + settings
      ↓
toolchains + language-host
      ↓
search + local-history + git
      ↓
editor-app 交互收尾与 Windows 发布
```

阶段之间不得通过复制编辑状态或绕过模块接口来抢进度；特别是 `EditorState`、插件清单、文档 revision 和工具路径解析必须各自保持唯一真相来源。
