# 15 — 升级已安装记录并通过新 SDK 重装插件

**Status:** ready-for-agent — 已发布，未开始实现；须等待全部阻塞项完成

**GitHub:** [#16](https://github.com/T-miracle/Editor/issues/16)

**Parent:** [设计基线 #1](https://github.com/T-miracle/Editor/issues/1)

## What to build

用户升级宿主后能看到旧包不兼容说明，原有设置与启用范围仍保留；使用新版 SDK 构建并安装对应新包后恢复使用。

完成新旧基线的安装数据桥接与公开构建分发流程，不提供永久旧运行协议转换层。为后续现有插件迁移提供稳定入口。

## Acceptance criteria

- [ ] 不兼容旧包在激活前拒绝，界面明确提示更新，不静默执行旧组件。
- [ ] 迁移旧安装记录、权限、全局与项目启用状态及私有数据，保持可恢复备份，不清空设置。
- [ ] 有限历史数据导入与通用运行逻辑分离，不把历史插件 ID 映射发展为永久执行分支。
- [ ] 宿主 SDK 导出、缓存及公开构建命令可构建新协议示例，不依赖本地宿主业务源码路径。
- [ ] 接口、包清单和打包资料一致，资源包不附带无用生命周期组件，README 随包可读取。
- [ ] 开发过渡保留的旧测试路径不作为正式兼容承诺；旧形式最终删除由收缩工单负责。

## Verification

用复制到临时目录的旧格式记录与数据测试升级，再通过公开 SDK 构建并重装新示例，验证状态保留与明确拒绝。

规格验收覆盖：T14、T24。

## Implementation guardrails

- 使用已确认的现有包管理器与编辑器集成测试边界，不新增插件专属测试入口。
- 只改变本工单范围，保留工作区已有改动；新增代码同时补充意图和不变量注释。
- 复用既有模块；必要的预重构先保持行为不变并通过相关回归，再加入新行为。
- 测试使用隔离目录与夹具，不操作用户真实插件安装数据；不提交 Git、不发布中间版本。
- 流程与契约细化若改变已确认产品行为，应先评审；不能以实现方便引入插件专属分支。
