# Nanobug 通用插件接口完整性审计

日期：2026-10-08。状态：调研与建议，尚未确认实施范围，不是发布验收或工单。

依据：当前工作区（HEAD `ebe40c270f2ceb616b12eca0125b461648ce4548`，包含大量未提交变更）、公开协议、运行时调用入口、宿主消费者、SDK 文档，以及三家编辑器的一手资料。代码盘点为静态核对，未重新运行全部功能测试；历史验收只作为线索。后续工作区变化需要重新核对。

**整合状态特别说明：** 当前 main 没有 XML 插件及新的语言接口，但 `codex/xml-language-tools` 分支 `e44a49606b8861afce7fdd068d09a04d39196a33` 已包含相关实现。已用 `git show` 核对该分支的 capability、language、structure、api 与语言编辑消费者。因此下文区分“main 已有”“分支已有待整合”和“仍需新增”，不能依据当前 main 的空缺重复开发分支已交付能力。`codex/host-messages` 的宿主 UI 工作也不能直接算作插件公开 API。

## 结论

Nanobug 已有能力协商、权限、WASM 隔离、资源归属、插件服务、原生 UI、文件显示布局、受控进程、运行配置和基础调试等底座。当前最影响社区开发的缺口，是通用文档访问与编辑事务、工作区文件操作和观察、编辑器内的语言与装饰贡献、宿主交互入口，以及网络和凭据能力。

尤其不能把下面几件事混为一谈：

1. 宿主已有 Git、搜索、通知或文件监听，不代表第三方插件有对应公开入口。
2. 能在自己的面板画文字，不代表能给原生编辑器贡献诊断、行内提示、补全或测试标记。
3. 能启动原生进程，不代表已提供可控、可移植的网络、文件、密钥或语言接口。要求普通插件捆绑辅助进程会提高安装成本及权限范围。
4. 有版本化插件服务，不代表标准业务契约已经齐全。测试、SCM、认证等仍需要大家共同遵守的数据和生命周期。
5. 接口类型存在，不代表 SDK、宿主消费、权限、撤销、文档和独立插件验证全部贯通。

不可能在首次上线前预知以后所有接口。更可靠的目标是：基础操作完整、常见插件类型有可验证的实现路径、新能力能够向前演进，而且插件在能力不足时能明确声明最低要求或降级。

三家产品不提供同一套扩展表面。不能因为某项是 Zed 内建功能，就推断 Zed 扩展可实现它；也不能把 IDEA 内部或实验接口当作稳定承诺。外部事实和稳定性细节见上述附件。

本报告状态含义：

- **已有**：在公开类型及相应实现/消费者中找到入口；不等同于本次完成跨平台验收。
- **部分**：基础入口存在，但还不能完成本行描述的通用场景。
- **分支已有**：在上述 XML 分支核实代码，当前 main 尚未纳入；先做整合与契约复用，不能按新功能重写。
- **缺口**：本次在公开操作、事件、清单贡献和标准服务契约中没有找到相应入口；不表示插件通过自建面板或已授权原生程序完全做不到。
- **扩展项**：涉及此前未确认的产品范围，需另行确定，不由本报告自动授权实现。

优先级：**P0** 为面向广泛社区开放前建议具备的基础契约；**P1** 为常见插件门类的重要覆盖；**P2** 为可分期的产品扩展。若首发明确只开放离线语言/预览插件，可以延后网络和认证，但必须同步限定生态承诺。所有优先级均为本次建议。

## 上线前建议形成的最小完整接口面

建议按以下十个深模块组织设计。名称为建议概念，不是已存在的 capability ID，也不建议因此创建十个新 crate。

1. **资源与文档**：统一资源身份、权限句柄、文档快照/范围读取、文档与文件事件。
2. **编辑事务**：单文档 batch、跨文件编辑计划、冲突预检、预览、提交与 Undo 约束。
3. **命令与贡献**：命令调用、位置、上下文、选择器、状态、卸载与失效。
4. **用户交互**：快选/输入/文件选择、通知/确认、进度、取消与所有权。
5. **语言提供者**：复用统一诊断/补全/编辑计划模型，让 LSP 适配器和 WASM 提供者进入相同消费路径。
6. **网络与身份**：网络传输、密钥、认证分开协商，在一个清晰的用户授权流程中组合。
7. **状态与配置**：私有持久状态、临时缓存、声明配置、变更和迁移。
8. **任务与生命周期**：按需激活、timer、后台调度、取消、限额、退役与回收。
9. **UI 与呈现**：现有原生 UI/Canvas/布局基础上补贡献位置、树、装饰、无障碍。
10. **Provider 与协作**：沿现有版本化服务补标准测试/SCM/认证等契约，以及有界数据流。

每个模块应把复杂性留在宿主实现里：插件提供业务数据和策略，宿主统一处理线程、生命周期、权限、冲突和绘制。两种互不依赖的插件能够通过同一接缝完成工作，才有证据说明接口可复用。

## 每个新接口都必须明确的规则

1. 目标是哪个资源/文档/工作区/实例；路径不是隐含授权，应用实例不借用当前工作区。
2. 哪个能力版本及安装权限，是否支持临时用户选择的外部文件授权，提供者能否转授。
3. 输入/输出类型、错误码、可空/可选/未知字段、大小和数量限制。
4. 文本坐标单位：现有 UTF-8 byte、LSP UTF-16、行列与 CRLF/非 BMP 字符转换必须明确；不能混用。
5. 接受、进度、完成、取消及资源释放的区别；deadline 与重试不得重放有副作用的操作。
6. 事件顺序、合并、丢失、补读、背压及迟到事件拒绝条件。
7. 并发与 revision：读快照可并行，写入经宿主事务；不能持有 UI 线程等待插件。
8. 保存/Undo/redo、插件故障与退出后的恢复，哪些外部副作用不可回滚。
9. 多提供者选择、结果合并及冲突；有效用户选择不能被安装顺序覆盖。
10. 平台支持与 unavailable 原因；不支持的特性在调用前可判断。
11. 用户可见行为：焦点、键盘、IME、本地化、主题、辅助功能、无障碍名称。
12. 兼容策略、独立插件范例、黑盒契约测试和开发诊断。

这些是后续验收建议，并非本次已经执行。至少为关键模块选择两个不同消费者，插件只通过正式 SDK/包进入宿主，不允许专属 ID 分支或测试专用宿主入口。

## 建议推进顺序

采用少量纵向批次，避免为每个方法拆工单和重复全量测试：

1. **资源/文档/编辑事务**：A01–A07 与 F01/F02 的必要部分，贯通脚手架和多文件修改。
2. **贡献/交互/诊断**：B01–B04、B09、C02/C03，贯通不用外部辅助程序的常见工具插件。
3. **网络/身份/后台生命周期**：D01/D03/D06/D08/D09，贯通两类云服务插件；OAuth 按首发场景纳入。
4. **高频 Provider 与原生 UI**：Tree、装饰、直接语言 Provider、测试和 SCM，按社区定位选择发布覆盖。
5. **SDK 与发行验收**：F03–F07、隔离开发配置、兼容测试和真实插件矩阵；此时汇总全量验收。
