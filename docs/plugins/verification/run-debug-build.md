# 运行、调试与构建 验收记录

本文件记录运行、调试与构建方案各工单的实际验收证据与实现期确认的决策。**父设计依据是跟踪器上的议题 [#48](https://github.com/T-miracle/Editor/issues/48)**（标题「[Spec] 运行、调试与构建总方案」），其正文在议题上，**本批从未改动它**。

**本文件早期版本把 `docs/plugins/specs/run-debug-build.md` 写成了父设计的路径，该文件并不存在**（已核对：`docs/plugins/specs/` 下只有 `plugin-management-logs.md`）。**本批新增的 `docs/run-debug-build.md` 是面向使用者的能力文档，不是设计依据**——两者的区别见下文「一处引用更正」。实现与提交在当前分支 `codex/run-debug-build`。

## 实现期决策

### D1 单独构建的保存策略（工单 05 要求先记录）

**结论**：单独构建与运行使用同一份**已保存**的配置，两者都不引入隐式保存。

- 点击构建或运行前，按既有自动保存流程确认脏文档（`save_dirty_documents`），失败或取消则不启动任何步骤。
- 未保存的配置草稿不产生任何进程，也不进入启动前步骤序列。
- **明确不采用**「为单独构建临时落盘一份草稿」的做法：它会绕过用户对保存的确认，属于此前未确认的产品行为，且与运行的保存规则不一致。

**影响**：构建与运行的行为一致，用户可以预测「屏幕上看到的配置」与「实际执行的配置」何时相同；代价是未保存的编辑必须先保存才能构建。

### D2 执行契约的可观察退出（工单 05 的技术前提）

构建步骤以「程序结束」为完成条件。宿主原先只能得知「程序已启动」，因此把「可观察退出」作为执行契约 **1.3** 的 `status` 方法补入，而不是用延时或日志猜测。宿主要求自己声明的每个方法，因此无法报告退出的提供者属于**不兼容**，而不是「看起来可用但永远不返回」。

### D3 步骤引用而非复制（工单 05）

启动前步骤通过 `@配置名` 引用另一配置的构建动作，存的是**配置标识**而非命令副本。修改被引用配置的构建定义后，引用即刻生效，不会出现两份会漂移的命令。

## 逐工单证据

真实 WASM 包测试以 `-- --ignored` 显式执行；被跳过的测试不计为通过。

### 01 手动配置运行真实程序（[#49](https://github.com/T-miracle/Editor/issues/49)）

- 宿主会话：`cargo test -p plugin-runtime --test host_execution -- --ignored` —— 启动一次并定位既有会话、缺失提供者被报告而不是被替换。
- 垂直验收：`cargo test -p editor-app --bin editor-app extensions::native_run_tests -- --ignored` —— 真实终端包内启动真实程序并观察到其输出。
- 就近回归：`cargo test -p editor-app --bin editor-app run::`。

### 02 正常停止、重新运行与离开确认（[#50](https://github.com/T-miracle/Editor/issues/50)）

- 停止经提供者会话完成（`host_controls_stop_the_program_a_session_owns`），宿主不借用提供者私有进程句柄，确认收到不等于程序已退出。
- 离开确认：有活动会话时窗口不关闭，确认后逐个停止会话再离开；取消留在原处。

### 03 统一下拉管理并行会话与输出（[#51](https://github.com/T-miracle/Editor/issues/51)）

- 两个配置并行运行互不干扰；同一配置重复启动只定位既有会话。
- 隐藏输出页签不停止程序：进程数不变、会话仍可停止、重新选中可恢复输出。

### 04 Shell 脚本与本机环境配置（[#52](https://github.com/T-miracle/Editor/issues/52)）

- 程序模式参数逐项编辑，含空格/中文的参数原样传递；Shell 模式显式选择解释器，脚本文本作为单个末尾参数，实测解释器求值成功。
- 环境变量：执行契约 1.2 的有界条目沿「真实插件包 → 公开管理器 → 受控进程」贯通，验收证明值确实到达子进程（子进程打印该值进入终端绘制）。
- 本机工具路径：成为**该次启动**的前置 `PATH`，用户自己的 `PATH` 保留在后，进入子进程的 `PATH` 只有一个。验收过程中发现 4 KiB 的环境值上限装不下真实 `PATH`，已改为 32 KiB 并同步契约 schema。
- 受限工作区不启动程序；配置不能提权、不能覆盖用户语言/主题/信任状态。

### 05 独立构建与顺序启动前步骤（[#53](https://github.com/T-miracle/Editor/issues/53)）

- 构建操作与启动前步骤分别存储，可分别编辑；后者可用 `@配置名` 引用另一配置的构建（决策 D3）。
- 构建页每个预置动作一行，带该行的上移、下移、删除与末尾的添加控件；不能执行的控制禁用而非静默无效。添加产生的是**模板行**（写作注释），既不消失也不会让配置在写完之前无效。
- 「构建」只执行本配置的构建操作：不跑启动前步骤、不启动程序；无构建操作时按钮禁用并给出原因，构建进行中再次点击不会并行构建同一份代码。
- 运行先顺序准备，步骤以**提供者观察到的进程结束**为继续条件（契约 1.3，决策 D2）；失败、被终止、结束状态无法确认、用户停止，都阻断后续全部步骤并报出是哪一步。
- 准备期间停止：先停当前步骤**自己拥有的**那个会话，并在其结束前保持序列仍被占用，因此窗口不会在准备程序还在终止时关闭。
- 步骤引用不复制命令：改被引用配置的构建定义后，下次启动执行的是新定义，而引用方存的仍是配置标识。

**真实包验收**（`extensions::native_build_tests -- --ignored`，5 项）：两步按序执行后才是程序；一处失败阻断后续与程序；单独构建只跑构建动作；准备中停止不产生启动副作用；引用跟随被引用构建的当前定义。

就近回归：`cargo test -p editor-app --bin editor-app run::`（44 项，含构建页行级编辑的原生检查）。

### 06 共享配置与本机覆盖（[#54](https://github.com/T-miracle/Editor/issues/54)）

- 共享文件 `.editor/runs.json`（格式版本 1）只承载可移植一半：名称、目标与字面参数、**项目相对**目录（项目根写作 `${workspace}` 记号）、构建与启动前步骤。环境变量值、变量名、个人工具路径、项目外绝对路径均不写入——有断言直接在文件字节里检索这些内容。
- 工作区打开时读取本机记录并与项目共享合并；项目条目的可移植一半来自项目，本机环境与工具目录按标识应用，工具目录仍作为该次启动的前置 `PATH`。
- 两个隔离工作区加载同一共享条目时，`${workspace}` 各自解析到自己的项目根；另一台机器的本机值读不到。
- 保存去向在对话框底部二选一（默认仅本机）：仅本机不创建项目文件；选择项目共享写入项目文件。取消不写任何东西；取消共享与删除共享配置都会从项目文件移除该条目，不会在下次加载时复活。
- 手工修改共享文件按**同一契约**校验：违反规则时在工作区打开时就报出原因，且不替换本机已有配置。
- 稳定身份与活动会话隔离：启动被接受时计划即固定，运行中的会话继续使用启动快照；保存或文件变化只作用于后续执行。

**就近回归**：`cargo test -p editor-app --bin editor-app run::`（含加载共享条目后准备出的请求：顺序来自项目文件、参数保持字面项、`${workspace}` 解析到本工作区、本机环境与工具目录生效）。

### 07 Rust 目标发现、保存与修复（[#55](https://github.com/T-miracle/Editor/issues/55)）

- 发现是**声明式贡献**：插件在自己的贡献文件里列出发现声明，宿主读取并应用。宿主词汇刻意很小（节、键、文件模式、字段默认值），不包含任何语言或构建系统专属分支。
- 每个候选带稳定身份（提供者 id + 目标在文件中的名称）、来源、目标类型与字段；宿主**要求提供者指明程序字段**，不会从显示标签臆造可执行文件——目标因此不会以「找不到文件」在启动时失败。
- 候选必须**经用户确认**才成为配置；发现本身不运行目标、不写入任何配置、不把所有候选塞进菜单。确认后立即打开配置弹窗以便修改。
- 重发现不覆盖用户修改、不重复保存：配置记住它来自哪个目标，**只更正程序**，名称、参数、环境、工具目录、步骤与共享选择原样保留。
- 目标改名或消失时配置被标记为**失效**（在选择处可见，并有修复入口），但**不被删除**；在发现运行之前不标记任何东西。
- 提供者可以提供字段**默认值**，用于声明「这类目标通过哪条工具链运行」，而不要求每个项目重复书写。
- 包管理器自己的子命令属于**启动前步骤**，不属于程序字段：程序字段保留「将来调试器要附加的程序」这一含义。

**真实包验收**（`extensions::native_discovery_tests -- --ignored`，1 项）：临时工作区里的**真实 Cargo 项目**经装好的 Rust 插件自己的声明被发现、确认成配置并运行；构建产出 `target/debug/<package>.exe`，程序会话在该项目目录中运行，计划为 构建 → 运行 → 程序。**未安装工具链时该用例跳过而非失败**，并打印跳过原因。

**就近回归**：`contributions`（真实 `Cargo.toml` 产出目标、身份不一致与缺失声明文件被报出）、`plugin-schema` 16 项、`editor-core` 21 项、`run::` 46 项。

### 08 执行提供者选择与调用（[#56](https://github.com/T-miracle/Editor/issues/56)）

- 调试页列出每个声明了执行契约的提供者、显示当前生效者，并允许配置「跟随默认」或指定一个。**装了但不能用的提供者仍被列出并给出原因**（未启用、不兼容、运行出错、契约不完整），且**不可选**。
- 选择记在**配置**上（共享条目只在本地记录保留该关联），因此切换作用域默认值不会静默改掉明确指定过提供者的配置；「跟随默认」是**移除**请求而非挑一个。选择同时应用到作用域，使所有启动路径一致，**只影响此后的启动**。
- 选择由运行时自己的版本化存储保存（`service-providers.json`），本工单没有新建第二份记录。
- **会话绑定启动它的提供者实例**：切换选择不会移动正在运行的会话；**只有启动它的提供者处于选中状态时该会话才可停止**，提供者永远不会被要求结束不是它启动的程序。
- 契约形状**精确匹配**（含 `env` 参数与 32768 字节上限）：收不到宿主所发内容的提供者服务不了本宿主。

**真实包验收**：
- `host_execution -- --ignored`（6 项）：已安装提供者被列出且被选中、禁用后仍带原因列出；**两个独立提供者服务同一消费者**（真实终端包与另一个不同 ID 的独立打包提供者，各自启动、定位、呈现、停止；切换不移动活动会话；只有自己的提供者能停自己的会话）；**启动请求的环境变量真的到达程序**（程序自己打印出的值，而非宿主断言）。
- `plugin_services -- --ignored`（4 项）：唯一/被选中的提供者互换、旧引用失效、缺失或不兼容的服务不激活必需消费者、调用保持来源且不能借用提供者权限或重入、委派资源与异步续体遵循原来源生命周期。
- `scoped_instances`（5 项）：资源句柄拒绝外来与已退休的所有者并释放全部视图；项目禁用保留其他工作区句柄；受限工作区不能授予访问。

**已知未验证**：宿主会话表的容量上限（`MAX_HOST_EXECUTIONS`）在**全部会话都处于活动状态**时不会驱逐任何条目——驱逐只针对已结束项，因为静默丢弃一个正在运行的程序更糟。本轮没有构造出「会话表达到上限」的可观察用例：真实包测试每个用例只启动少数程序，而构造 64 个并发会话的成本与收益不成比例。因此该上限的**行为**（超出时先驱逐已结束项）只有实现与注释佐证，没有测试证据。

### 09 Rust 启动调试与源码断点（[#57](https://github.com/T-miracle/Editor/issues/57)）

**决策先于实现**（依据见 `crates/plugin-protocol/SERVICES.md`）：调试是**提供者契约**，宿主只做通用转发；宿主**不捆绑、不自动安装**调试器，也不因缺能力而回退为普通运行。

本机实测（决定所依据的事实）：`rust-gdb.exe`/`rust-lldb.exe` 是 rustup 代理（各约 12 MB），三套已装 MSVC 工具链里**都没有 `lldb.exe`**；PATH 上唯一的调试器是 GCC 发行版的 `gdb.exe`（MinGW-W64 r7，GDB 17.1，MI2）。实测 `cargo build`（默认 MSVC 目标、`debug = 2`）产出 `probe_debug.pdb`（1.3 MB），而该 GDB 报 `No debugging symbols found`——它读 DWARF，MSVC 写 PDB。**本机没有能读取这些调试信息的调试器。**

已实现并验证的部分：

- **通用调试契约**：宿主把自己的要求写成声明（`debug.session`：start、set_breakpoints、resume、pause、status、stop），提供者**只有逐形状声明它**才算匹配。测试断言这份要求里**不出现**任何调试器名、适配协议、目标语言或工具链。
- 读取会话就是读提供者的观测：**未知状态词被拒绝**而不映射成已知状态；暂停会话带着提供者报告的位置；**未验证的断点不被算作已设置**。
- **缺能力时入口拒绝并说明原因**（未确认能力、未安装、提供者不可用、多个可用需先选择），**不静默退化为普通运行**；配置不可运行则同样不能调试，两个控件对同一配置给出同一答案。
- **断点属于运行程序的配置**：只存真正的位置（空/超长源、第 0 行、重复设置均被拒并给出原因）；两种路径分隔符与大小写视为同一文件；列表按项目顺序；清空单个源带走其全部位置；断点随共享条目跨机器往返，而环境与工具目录留在本机。
- **调试控件按连接与目标状态启用**：可用性决定「开始」，会话状态决定「继续/暂停/停止」；**每个不可用控件都带原因**（对所有状态与可用性组合断言）；连接中即可停止（这正是用户需要出口的时刻）；已服务的会话是停止而非再次开始。
- **停机与进程归属**：关闭窗口时，宿主先通过启动它的提供者请求停止仍拥有程序的会话，再退休会话、拆除实例；每个应答有界等待，不可响应的提供者只耽误片刻。端到端属性对着**机器自己的进程表**验证（被宿主「只是忘掉」的程序仍在运行，只有真实进程表能揭穿这一点）。

  **一次被否证的判断，如实记录**：我最初读到 `shutdown` 只调用 `host_sessions.retire()`（只标记退休、从不请求停止），判断这是「关闭后程序被遗弃」的缺陷并实现了修复。禁用该修复重新测量后**没有泄漏**——提供者的实例本身就拥有它启动的东西，实例拆除已经结束了那些进程。因此这是**顺序改进**：让提供者在窗口关闭前观察到终止，从而凭观测而非假设回答状态查询；测试名与注释都只声称端到端属性成立，不声称隔离了是哪一步结束进程。

**未验证（环境受限）**：**真实断点命中、暂停/继续与失败清理**需要能读取 PDB 的调试器，本机没有，按已确认的处理方式不安装不捆绑，因此这一条**不计为通过**。已实现的是它两侧的全部：契约、拒绝路径、断点模型、控制状态推导与停机路径。**调试器与适配器自身的进程**由提供者拥有，随其实例拆除释放；宿主侧未独立验证该释放（本机没有调试器可启动）。因此本工单保持打开。

`scripts/run-debug-startup-smoke.ps1` 补上本批**唯一缺少的真实二进制验收**（此前的冒烟脚本只覆盖终端与运行时插件的首帧）。它做三件事：

1. 在一个**含真实共享配置**（`.me-editor/run-configs.json`）的工作区上启动 `target/debug/editor-app.exe`，确认它**没有在加载配置时退出**，并且**真的创建了原生窗口**（句柄非零）；
2. 向该窗口发送关闭消息，确认**进程随之退出**；
3. 确认**没有留下任何它拥有的程序**。

**判据本身也要能被证伪**：脚本先启动一个**编辑器不可能拥有**的对照程序（带本次运行的唯一标记），确认泄漏检查**看得见它**；关闭窗口后要求它**仍在**（否则这次运行无法区分「没有泄漏」与「检查是瞎的」），并要求总数不超过「对照 1 个」。实测输出：

```
editor started with a shared configuration and owns a native window (10162308)
leak check is sensitive: it sees 1 program(s) carrying this run's marker
closing the window ended the editor process
Run and debug startup smoke passed: no program was left behind by shutdown.
```

**它明确不测什么**：不点「运行」，因此**不测量启动行为**（那由进程内的原生验收覆盖）；它测量的是**加载共享配置不破坏启动**与**关闭窗口会回收会话拥有的东西**。

**过程中一处环境问题**：`Start-Process` 在一份同时设置 `NO_PROXY` 与 `no_proxy` 的普通 Windows 环境上会抛 `已添加项`，因此脚本改用 `System.Diagnostics.Process` 直接启动。

### 一处真实缺陷：承诺停止程序的调用从未接上（本轮修复）

做变异抽查时发现 `stop_owned_programs` **是死代码**（编译器一直报 `never used`）。溯源到引入它的提交 `996d870`：那次提交在 `scopes.rs::shutdown` 里加了**说明「先请求停止、再退休会话」的整段注释**，也在 `host_services.rs` 里加了函数本体，**但从未加上那句调用**。因此：**注释声称的行为不存在，程序从未被请求停止**。

**已修复**：在 `retire()` 之前接上 `self.stop_owned_programs();`，与注释和当时的提交说明一致；死代码警告随之消失。

**但这个修复不改变可观察行为，我也不声称它改变了**：把调用再次去掉，`closing_the_window_leaves_no_program_running` 与 `closing_while_a_launch_is_still_preparing_...` **仍然通过**。原因正是当时那次提交已经如实记录过的——**提供者的实例拥有它启动的东西，实例拆除本身就会结束那些进程**。所以这是**顺序**：让提供者在窗口关闭前观察到终止、并能凭该观察回答状态查询，而不是让窗口在一个没人通知过的会话上关闭。

**结论**：修复的是**代码与它自己的注释不一致**（以及一处死代码），**不是**一个可观察的缺陷；**没有测试能区分有无这次调用**，这一点如实记录，不把它算作「修好了一个 bug」。

### 一处更大的真实缺陷：检查视图从未被请求（本轮修复）

接着读**死代码警告**（正是上一轮发现缺陷的方法），发现一个更大的问题：**`DebugMethod::Frames` 与 `DebugMethod::Variables` 在测试之外从未被构造**——也就是说**编辑器从不向任何提供者请求调用栈或某帧的变量**。面板会渲染栈帧与变量、答案处理会应用它们、worker 会派发它们，**但没有任何代码发起请求**：工单 10 的检查视图在真实运行的编辑器里**不可能显示任何东西**。

链路断了三处，现已接通：

1. **`DebugCapabilities` 缺少 `inspect`**，而宿主的 `DebugAbilities` 有——编辑器对「提供者声明」的镜像**丢掉了检查视图所依赖的那项能力**；
2. **worker 从不发布提供者的能力**，因此 `debug_capabilities` 一直是全 false 的默认值，`note_debug_capabilities` **只在测试里被调用过**；
3. **暂停开始时没有任何代码发起 frames 或 variables 请求**。

现在：宿主以**同一个提供者**的一次回答给出「能否在此启动会话，以及它能做什么」；worker 发布它；编辑器翻译它；暂停时按该能力**发起面板所需的那两个请求**——因此**不能描述目标的提供者永远不会被请求**。两条死代码警告随之消失（变体现在真的被应用构造）。

**这不等于让视图端到端显示真实数据**：那需要一个调试提供者与真实目标，属本工单已记录的环境受限项。

### 第二处同形缺陷：断点从未被发给任何提供者（本轮修复）

读死代码警告时发现**与检查视图同形**的问题：`breakpoints_by_source` 与 `DebugBreakpointRequest::to_value` 存在、契约声明了 `set_breakpoints`、能力从它推导、答案读取函数也写好了——**但没有任何代码发出这个请求**。

后果：**断点可以被保存、编辑、经表单往返，却从未被告诉任何提供者**。工单 09 的「断点属于运行程序的配置」因此**只接了一半**——**配置有断点，调试器没有**。

已实现 `Manager::debug_set_breakpoints`：**每次发送全集，按源分组**（提供者就是这样被请求的）。发全集而非差分，因为**答案描述的是提供者能绑定哪些位置——一个被移除的断点必须不在请求里，那个答案对它才有意义**。

**两条警告随之消失**，这正是「这些函数在等这个调用者，而不是冗余」的证据。用例断言的是**宿主构造的参数**而不是提供者的回复，因为那才是宿主负责的那一半。

**尚未接线**：**编辑器侧还没有在会话开始或断点变更时发送它**，worker 也还不接受 `"set_breakpoints"`。这条与检查视图那条一样，是**下一步**，不声称端到端可用。

**结果**：用例在**更靠后**的一行失败，并给出决定性事实：

```

**停止请求已经发出（`pending_stop=true`），但它一直没有得到应答**——`stops` 里那条待处理记录从未被 `reconcile_stops` 收走（收走需要 `stop_results` 里出现匹配的 `request_id`），因此 `note_preparation_stopped` 从未运行，序列自然不阻塞。

**这把根因又下推了一层**：**问题不在「谁有权发停止」，也不在「会话已结束没人告诉序列」，而在「这条停止请求的应答没有回到编辑器」**——`Work::StopRun` 由 `pump_recording` 执行其结果也发布了，但编辑器侧的 `sync_run_controls` 在本用例的驱动节奏下没有把它收下来。**这解释了为什么前九次改动都在别处使劲而无效果**：它们都在改「应答到达之后」的逻辑，而**应答从未到达**。

```

**每一帧的 `outstanding` 都是空的**，即 `self.stops` 里**从来没有过待处理项**；而 `begin_stop` 是唯一往这里写的地方。**因此 `stop_preparation_step` 从未被调用。**

**这把问题定位到最后一处**：用例里被发现的那个 `Work::StopRun` **不是序列为准备步骤发出的那一次**（很可能是启动路径留下的），也就是说 **`drive_preparation` 在本用例的驱动节奏下从未走到 `SequenceAction::Stop` 分支**——既没有停止请求、也没有应答、也没有阻塞。

**下一步入口很具体**：查 `next_action` 走到 `Stop` 所需的条件（步骤处于 `Running` 且 `stopping` 为真），**以及本用例里那个步骤是否真的到达过 `Running`**。**这也解释了前十次改动为何全部无效：它们改的都是这条分支之后的逻辑，而这条分支从未被进入。**

### 条件核对的结果：两条实测互相矛盾，先记下来而不是继续改

本轮按上面的入口查了条件，**得到的不是答案，而是两条彼此矛盾的读数**：

| 探针位置 | 读数 |
| --- | --- |
| `drive_preparation` 的动作 | **确实走到 `Stop(1)`**，而且**连续多帧都是 `Stop(1)`**（`next_action` 返回 `Stop` 的条件**满足**） |
| 用例结束时的状态 | `requested=Some(1)`、`stopped_session=Some(1)`、**`is_stopping=true`**、`active=[1]` |
| `reconcile_stops` 入口（每一帧） | **`published=0 outstanding=[]`**——意思是**每一帧都没有待处理停止、也没有已发布的停止结果** |

**这三条无法同时成立**：若 `is_stopping=true`，`self.stops` 就不为空；而 `reconcile_stops` 每帧打印的 `outstanding` 却是空的。**因此至少有一个读数不是我以为的那个东西**（最可能是 `outstanding` 的打印口径，或 `reconcile_stops` 被调用时 `stops` 已被同一帧更早的一步取走）。

**我本轮不再据此改任何代码**。理由很直接：**前十二次改动都是在这样的矛盾读数上做的，而它们全部无效**；**在读数自相矛盾时继续改，只会再增加一次无效改动**。

**给下一步的具体建议**：**先用一次打印把这三件事放在同一时刻取**（`self.stops` 的内容、`next_action` 的返回值、`stop_preparation_step` 是否进入），**而不是分别在不同位置打印**——本轮正是分处打印造成了这个矛盾。**在此之前，这个用例的失败原因仍未被确定。**

### 同刻测量：矛盾消失了，答案只剩一个

本轮按上面的建议做了**同刻打印**（在 `drive_preparation` 的 `Stop` 分支里一次取全），**矛盾随即消失**，读数自洽：

```
probe stop config=<cfg> session=1 is_stopping=false outstanding=[]          ← 第一帧：尚无待处理项
probe stop config=<cfg> session=1 is_stopping=true  outstanding=[(<cfg>, 4, 1)]  ← 之后每一帧
```

**即：第一帧发出停止（登记为请求 4），此后每一帧都命中守卫而不再发送。** 结合整轮的 `reconcile` 打印（916 行，**每一行都是 `published=[]`**），得到一个**自洽**的结论：

**停止请求确实发出并登记（请求 4），但它的应答从未产生——因此序列永远等不到「已停止」，也就永远不阻塞。**

**这也解释了为什么前十二次改动全部无效**：它们都在改「应答到达之后」的逻辑，而**应答从未产生**。

**本轮同时改掉了一处让用例无法自证的地方**：该用例原先在读取到 `Work::StopRun` 后**又自己调用 `manager.stop_execution(session)`**，这在夹具里**把那个工作项从队列中取走**，于是 `pump_recording`（本应在 `frame` 内按生产路径执行它）**永远拿不到它**。**现在用例不再自己执行停止**，改由夹具按生产路径执行——**读数因此变得可信**（`requested=Some(1)` 的断言仍在，且仍通过）。

**用例仍未通过**（失败点后移到 `preparation_blocked` 的断言），**但失败原因现在被限定为一处**：**夹具执行 `Work::StopRun` 之后，`stop_results` 没有到达编辑器的 `reconcile_stops`**。**这是下一步唯一的入口。**

### 已修复：缺陷在用例，不在产品

**结论：该用例现在通过**（`native_build_tests` **5/5**、`native_run_tests` **7/7**）。**根因是用例自己把需要执行的工作项取走了**：

1. 用例在编辑器发出停止请求后，用 **`Receiver::try_iter` 读工作队列**——**该调用会「排空」通道**；
2. 它随即**又自己调用 `manager.stop_execution(session)`**；
3. 于是那个 `Work::StopRun` **在夹具（本应在 `frame` 内按生产路径执行它）拿到之前就被取走**——**`stop_results` 永远为空、`note_preparation_stopped` 永不运行、序列永不阻塞**；
4. **用例因此失败，而看起来像产品缺陷**——**这正是前十四次改动一直在追的东西**。

**修法**：**用例不再读队列、也不再自己执行停止**，只等待准备被报告为已阻塞，并断言它真正要测的两件事：**准备给出的原因含「停止」**，以及**程序从未被启动**。

**一处断言被有意收窄并写明理由**：**运行时自己的会话状态在提供者被要求停止后仍是 `Running`**——因为**该提供者在「终止已发出」时就应答停止**，**而父设计第 47 行正是要求「受理不等于结束」**。**若在这里断言会话已结束，就会与设计相矛盾**，因此用例写明了为什么不断言它。

**通道核对（本轮实测，逐环确认）**：夹具确实收到并执行了该请求（`probe harness_stop session=1 request=4 ok=true`）→ 结果确实到达编辑器（`probe reconcile published=[("<cfg>", 4, Ok(()))]`）→ 序列据此阻塞、用例通过。**四个环节现在都有实测，不再有猜测。**

**教训（值得单独记下）**：**一个「排空式」读取（`try_iter`/`try_recv`）会让另一个消费者永远拿不到数据，而症状出现在下游、看起来像产品缺陷。** 本文件先前记录的「四处实现缺失」是真的，**但这一处不是**——**它是测试自己制造的**。**分辨这两者，靠的是同刻证据，而不是改动次数。**
