## 补充更正：先前引用的「父设计第 47 行」不是父设计

上一条更正说明里，我引用了「**父设计第 47 行**」来论证那条用例里一处断言的收窄。**这个引用方式不准确，需要更正。**

### 事实

- 我引用的那句话（「停止请求被受理不等于程序已结束：状态来自提供者的观察」）出自 **`docs/run-debug-build.md`**；
- **该文件是本批新增的、面向使用者的能力文档**（首行为「本说明面向使用者，介绍如何…」），由本分支的提交 `cc2abe1` 加入；
- **父设计是跟踪器上的议题 #48**（「[Spec] 运行、调试与构建总方案」），**本批从未改动它**。

**因此我不应当把本批自己写的文档称为「父设计」，更不应当用它来充当「设计要求」的外部权威**——那等于用自己写的东西为自己的改动背书。

### 对那条用例修法的影响

**结论不变**：该用例的失败根因是**用例自己用 `try_iter` 排空工作队列、并在夹具拿到之前自行执行了停止**；修法（不再排空、不再自行执行停止）**不依赖任何文档条文**，它依赖的是实测：

```
probe harness_stop session=1 request=4 ok=true      ← 夹具确实执行了该请求
probe reconcile published=[("<cfg>", 4, Ok(()))]    ← 结果确实到达编辑器
```

**但论证方式需要改**：那条用例里「不断言运行时会话状态」的收窄，**理由是**「该提供者在终止已发出时就应答停止，因此运行时状态不是这条用例要测的东西」——**这是实测事实**；**而不是**「父设计要求如此」。

### 我为什么会犯这个错

我把**自己这一批产出的文档**当成了**既有的权威依据**，并在多轮里反复引用它、逐步把「我写的一句话」升级成「设计的要求」。**这类错误比一个失败的测试更值得警惕**：它会让后续结论建立在自造的权威上，而且**看起来完全合理**。

**记录在此，供后续核对者注意**：引用依据时应当指明它**是谁、何时、以什么身份**产生的；**本批自己产出的文档不能作为本批的验收依据。**
